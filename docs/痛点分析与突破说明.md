# E志愿志愿服务管理系统 痛点分析与功能突破说明

本文件记录本项目在 V1.0 基础上所做功能突破的来源：先调研当前志愿服务平台在公开报道、政府通报与行业
调研中暴露出的真实痛点，再针对可在本平台内闭环解决的痛点完成实现，并给出可复现的验证方式。

调研时间基准：2026 年 9 月。

---

## 一、痛点清单（调研结论与证据）

| 编号 | 痛点 | 典型表现 | 证据来源 | 本项目对策 |
| --- | --- | --- | --- | --- |
| P1 | 志愿服务时长被“商品化”，刷时长、买卖时长、伪造记录形成灰色链 | 出现“在家打卡积累 300 小时”“几十元购买时长与星级证明”等交易，中央社会工作部等部门为此部署专项整治 | 中央社会工作部典型案例通报 <https://www.quanjiao.gov.cn/zwdt/tzgg/392396127.html>；澎湃新闻报道 <https://www.thepaper.cn/newsDetail_forward_33184233>；中新网评论 <https://www.chinanews.com/ll/2025-07-28/10454718.shtml> | 已落地：可信签到与时长核算（见突破一） |

| P8 | 激励回馈单一，时长缺乏可兑换价值，志愿者难以长期坚持 | 时长在积分落户、子女入学、信用评价中的回馈机制不健全，星级认定流于形式 | 凤凰网河南调研 <https://hn.ifeng.com/c/8qDqIqIPRRO>；网易报道 <https://www.163.com/dy/article/KQG8R3HD0525PS8H.html> | 已落地：累计时长自动评定星级 + 成长进度 + 信用分（见突破二、突破三） |

## 二、已落地的突破

### 突破一：可信志愿服务时长（签到码 + 时间窗口 + 地理围栏 + 异常复核）

针对 P1、P2。核心思路是让“时长”不再由任何一方单独写定，而是由**现场签到码、时间窗口、地理位置、
组织复核**四个环节共同约束，任一环节存疑即进入人工复核。

| 规则 | 具体取值 | 落点 |
| --- | --- | --- |
| 签到码 | 每个活动生成 6 位随机签到码（字符集剔除易混淆的 `0/1/I/O`），由志愿者组织在活动现场公布，可随时重新生成 | `activity.activity_checkin_code`，`CheckInServiceImpl` |
| 签到窗口 | 活动开始前 60 分钟 至 活动结束时间 | `volunteer_checkin` 存储过程 |
| 签退窗口 | 活动结束时间后 120 分钟内 | `volunteer_checkout` 存储过程 |
| 地理围栏 | 活动申报时记录经纬度与半径（默认 300 米），签到/签退均记录志愿者坐标与距离 | `activity_activity_latitude/longitude/radius`、`checkin.checkin_distance/checkin_outdistance` |
| 距离计算 | 数据库 `ST_Distance_Sphere` 球面距离，超出围栏即标记异常 | `volunteer_checkin`、`volunteer_checkout` |
| 异常标记 | 超出围栏、缺少定位、服务时长小于 0.5 小时或大于计划时长 2 倍加 1 小时，标记 `checkin_flag = 2` | `volunteer_checkout` |
| 时长核算 | 签退时按签到签退时间自动核算（保留两位小数），写入报名记录 | `volunteer_checkout` |
| 时长生效 | 必须经志愿者组织复核确认后才计入志愿者累计服务时长，并奖励信用分 | `organization_check_checkin` |
| 防重复 | 一次报名只对应一组签到签退记录；已签到的报名不可撤回 | `volunteer_checkin`、`volunteer_cancel_participate` |

数据对象：`activity`（签到码、经纬度、围栏半径）、`checkin`（签到码、坐标、距离、轨迹标记、复核意见）。

### 突破二：供需智能匹配与志愿者成长档案

针对 P4、P5、P8。活动申报时登记服务技能标签与活动地点，志愿者在个人档案中登记技能标签与常住定位，
平台按四个维度计算匹配度并给出可读理由，志愿者工作台按匹配度降序推荐活动。

| 维度 | 满分 | 计算规则 |
| --- | --- | --- |
| 技能匹配 | 40 | 活动技能要求命中比例 × 40；活动未设置技能要求时记 20 分 |
| 距离 | 30 | 1 公里内满分；2 万米外 0 分；区间内线性衰减；未设置定位时记中性 15 分 |
| 时间 | 20 | 与志愿者已报名（待审核/已通过/候补）的活动时间不重叠记满分，冲突记 0 分并列出冲突活动 |
| 组织历史参与 | 10 | 志愿者在该活动所属组织已报名活动 1 次及以上记满分 |

技能标签固定为 10 项（助学支教、助老服务、环保公益、社区服务、医疗健康、应急救援、大型赛会、
文化宣传、心理疏导、信息技术），志愿者与活动共用同一标签集合，保证可匹配。

成长档案：按已核定累计服务时长自动评定星级（100 / 300 / 600 / 1000 / 1500 小时对应一至五星），
并给出距离下一星级还需的时长。

落点：`MatchCalculator`（纯函数、可单元测试）、`MatchingServiceImpl`、`ActivityMatch` 视图、
`VolunteerStarEnum`、`volunteer_skill` 与 `activity_skill` 表。

### 突破三：报名名额控制、候补队列与爽约信用

针对 P3、P8。报名与审核全程由数据库存储过程在行锁保护下完成，避免并发超额。

| 规则 | 说明 |
| --- | --- |
| 报名前置校验 | 活动状态、报名截止时间、重复报名、信用分（低于 60 分暂停报名） |
| 名额控制 | 已通过人数达到需求人数时不再直接受理，自动进入候补队列（报名状态 `3`） |
| 审核通过校验 | 加锁复核剩余名额，名额已满时拒绝通过并给出原因 |
| 撤回递补 | 志愿者撤回已通过的报名后，最早进入候补队列的志愿者自动递补为待审核 |
| 活动结算 | 活动结束后由志愿者组织结算考勤，已通过报名但无签退记录者记为爽约，扣减信用分 10 分 |
| 信用分 | 初始 100，服务时长复核通过 +2（上限 120），爽约 −10（下限 0），低于 60 分暂停报名 |
| 幂等 | 活动仅可结算一次，签到记录仅可复核一次 |

落点：`volunteer_apply_activity`、`volunteer_cancel_participate`、`organization_check_volunteer`、
`organization_settle_activity` 存储过程与相关页面。

### 突破四：可校验的志愿服务证明

针对 P6、P7。志愿服务证明汇总志愿者已核定累计服务时长、已核定服务记录与星级，并附 16 位校验码：

```
校验码 = HMAC-SHA256(平台密钥, 志愿者编号 | 累计服务时长 | 已核定记录数) 的前 8 字节，大写十六进制
```

校验码由累计服务数据直接决定，数据一旦变化校验码随之变化，任何人无法在不掌握平台密钥的情况下伪造。
门户提供公开校验入口，输入志愿者编号与校验码即可核验，并展示姓名（脱敏）、累计时长、活动数、
星级与签发日期。

落点：`CertificateCodeUtil`、`CertificateServiceImpl`、`/volunteer/certificate` 与
`/certificate/verify`、`templates/volunteer/certificate.html`、`templates/portal/verify.html`。

### 突破五：审核透明化与修改后重新申报

针对 P9、P10。平台管理员驳回志愿活动时必须选择结构化原因（活动方案不完整、人员安排不明确、
活动时间或场地存在冲突、活动信息缺失、存在安全风险、其他原因），拒绝无原因驳回；志愿者组织端
展示审核时间、驳回原因与修改次数，并支持在弹窗中修改活动信息（含技能标签、活动定位、签到围栏半径）
后重新提交审核，活动回到“审核中”状态并记录修改次数。

落点：`ActivityRejectReasonEnum`、`admin_check_activity`、`organization_revise_activity` 存储过程、
`templates/admin/act_not_audit.html`、`templates/org/act_not_audit.html`。

### 突破六：密码加盐存储与历史密文平滑升级

针对 P11。新密码使用 `PBKDF2WithHmacSHA256`（120000 次迭代、16 字节随机盐）摘要后存储，
同一密码两次加密结果不同。历史使用 MD5 摘要存储的账号在登录校验通过后由平台自动改写为加盐密文，
无需人工重置密码；同时删除了 `organization`、`admin`、`volunteer` 三张业务表中重复的密码列，
登录凭据统一保存在 `e_user` 表，避免出现两处凭据不一致。

落点：`SecurePasswordEncoder`、`PasswordUpgradeServiceImpl`、`WebSecurityConfig`。

### 突破七：志愿者工作台（补齐志愿者侧空缺）

V1.0 中志愿者仅能注册，无法使用平台。本次新增志愿者角色（`ROLE_VOLUNTEER`）与个人工作台：
个人工作台（服务数据、成长进度、推荐活动、最近报名）、活动广场（匹配度排序与报名）、
我的报名（报名状态、签到签退、服务时长与复核状态、撤回报名）、我的档案（技能标签与常住定位）、
志愿服务证明。注册即开通登录账号，凭注册编号与密码登录。

## 三、三批基础能力补齐（本轮新增）

在突破一至七的基础上，按“主流程完整性 → 运营效率 → 预留功能落地”的顺序补齐了平台的基础能力。

### 批一：主流程完整性

| 能力 | 说明 | 落点 |
| --- | --- | --- |
| 活动状态流转 | 志愿者组织可人工把活动置为进行中或已结束；同时由定时任务按活动时间自动流转（未开始且已到开始时间→进行中；已过结束时间→已结束） | `organization_change_activity_state`、`activity_state_refresh` 存储过程、`PlatformTaskScheduler` |
| 活动结算前置 | 结算要求活动已结束（含人工提前结束），避免活动进行中就统计爽约 | `organization_settle_activity` |
| 服务时长补录 | 志愿者组织可为线下或未在平台签到的服务补录时长；补录必须晚于服务结束时间、单条不超过 24 小时、不得与已有服务记录时段重叠 | `organization_record_service_hours` |
| 补录复核分离 | 平台签到记录由志愿者组织复核，**补录记录改由平台管理员复核**，录入方与复核方分离 | `admin_check_manual_checkin`、`checkin_source` |
| 报名二次确认 | 报名通过后志愿者需在「我的报名」中确认参加；活动开始前 24 小时仍未确认且报名已满 12 小时者自动释放名额并递补候补志愿者 | `volunteer_confirm_participate`、`participate_confirm_expire` |
| 站内通知 | 报名提交、报名审核结果、参加确认、时长复核结果、活动公告、活动开始与结束等节点写入站内通知，志愿者与组织各有消息页 | `notification` 表、`NotificationService` |
| 通知公告与附件 | 平台管理员发布通知公告并可上传附件，公众门户展示公告与附件下载 | `policy_announcement`、`policy_file`、`AnnouncementService` |
| 门户数据绑定 | 门户首页的通知公告、近期活动、志愿者组织由公开接口读取真实数据，替换原来的静态示例内容 | `PortalSiteController`、`PortalMapper` |

### 批二：运营效率

| 能力 | 说明 | 落点 |
| --- | --- | --- |
| 分页与检索 | 全部列表接口统一 `page`/`size`/`keyword`，响应统一 `list`/`total`/`page`/`size`；活动、报名、服务记录、通知、审计等列表均可分页与按关键字检索 | `PageSupport`、各 Mapper 分页语句 |
| 数据导出 | 志愿者组织可导出活动报名考勤名单与服务时长明细；平台管理员可导出志愿者名册与活动清单，CSV 带 UTF-8 字节序标记，含逗号与引号的字段按 RFC 4180 转义 | `OrgExportService`、`ExportService`、`CsvExporter` |
| 审核后调整报名 | 志愿者组织可移除本组织活动名单中的报名；已通过的报名移除后释放名额并自动递补，已核定时长的报名不允许移除 | `organization_remove_participate` |
| 修改与重置密码 | 志愿者可自助修改登录密码（校验原密码、长度 8～20 位、不得与原密码相同）；平台管理员可重置任意账号密码并回传一次性新密码 | `UserAccountService` |
| 账号管理 | 平台管理员可开通志愿者组织账号（不填密码时平台生成并回显一次）、启用或停用组织与志愿者账号（停用后无法登录） | `admin_create_organization`、`admin_set_account_enabled`、`AdminAccountService` |
| 操作审计 | 活动审核、重新申报、状态流转、结算、报名审核与移除、服务时长与补录复核、账号开通与启停、密码重置与修改、公告发布删除、志愿秀删除等操作写入审计日志，可按类型与账号查询 | `audit_log` 表、`AuditLogService`、`AuditActionEnum` |

### 批三：预留功能落地

| 能力 | 说明 | 落点 |
| --- | --- | --- |
| 志愿培训 | 志愿者组织为活动创建与维护培训安排，登记志愿者培训情况；志愿者在个人工作台查看本人已报名活动的培训 | `training`、`volunteer_training_situation` 表、`TrainingService` |

### 批四：可信时长加固（针对反作弊）

在三批基础能力之上，针对“时长注水、代签、事后异常”三类风险再做一层加固：

| 能力 | 规则与落点 |
| --- | --- |
| 短时轮换签到码 | 签到码不再固定：由活动**签到密钥**与时间窗口派生，每 120 秒轮换一次，兼容上一窗口（输入耗时与时钟偏差）；志愿者组织可「更换密钥」立即作废旧码。落点：`activity_checkin_secret`、函数 `activity_checkin_code`、`volunteer_checkin` |
| 服务对象反向确认 | 志愿者组织为一条服务记录生成**服务确认单**（服务对象名称 + 预留手机号），平台下发 8 位确认码由组织交给服务对象；服务对象在公开页面用「确认码 + 本人手机号」确认或否认本次服务，无需登录。**确认**表示该次服务获得双方验证；**否认**且该时长已计入时，平台立即冲销（扣回累计时长与信用分）并通知志愿者组织核实。落点：`checkin_objectname/objectphone/confirmcode/objectconfirm`、`organization_issue_confirm_sheet`、`service_object_confirm`、门户 `/portal/service-confirm.html` |
| 时长异常规则引擎 | 引入规则表 `anomaly_rule`（阈值可配置、可停用），当前内置四条规则：单日累计上限 12 小时、单条上限 12 小时、夜间（0—5 时）服务、同一报名补录条数上限 3 条。命中规则的记录**不计入**累计时长，转入平台管理员裁定队列；管理员可「确认计入/维持计入」或「驳回/冲销」；另有定时巡检把事后出现的单日超限记录标记出来供裁定。落点：`anomaly_rule`、`service_anomaly_check`、`service_anomaly_scan`、`admin_check_checkin`、管理端 `/admin/review/anomalies` |

## 四、尚未覆盖的方向

以下痛点在本项目中**未实现**，仅作为后续演进方向，不代表已完成：

1. **设备指纹与同设备多账号检测**：签到码已短时轮换、时长已有规则引擎，但平台未采集设备指纹，
   无法识别“同一台手机为多个账号签到”这类批量代签（异常规则当前覆盖时长维度，不覆盖设备维度）。
2. **跨平台数据导入导出与对账工具**：当前仅提供带校验码的证明与本平台 CSV 导出，未实现其他平台记录的
   批量导入、账号映射与差异报表。
3. **组织实名认证与白名单**：未实现统一社会信用代码核验、官方标识与山寨组织名称拦截。
4. **内容风控**：未实现“卖时长/买证书”关键词与图文内容的风控（时长维度已由异常规则引擎覆盖）。
5. **站外触达与账号自助找回**：站内通知已实现，但未接入短信/邮件/微信提醒；忘记密码仍需管理员重置，
   未提供邮箱或短信自助找回。
